# 前端路由与会话管理

本文档记录 `fst` 项目前端路由与会话管理的实现细节，包括运行时路由模式、标签页存储隔离、管理员代登录安全加固等内容。

## 运行时路由模式

### 设计目的

前端支持用户端和管理端两种路由模式，需要避免以下问题：
- 管理员入口从用户窗口打开时继承 opener 的 sessionStorage 副本
- 跨端标签页污染（用户端和管理端的标签页状态混淆）

### 实现位置

- `frontend/src/router/runtime-mode.ts`：运行时路由模式管理
- `frontend/src/store/tab.ts`：标签页存储隔离
- `frontend/src/store/auth.ts`：认证状态管理
- `frontend/src/layouts/index.vue`：布局组件路由模式判断

### 核心实现

#### 1. 运行时路由模式管理

```typescript
// frontend/src/router/runtime-mode.ts
export function getRuntimeRouteMode(): AppRouteMode {
  return window.__APP_ROUTE_MODE__ || 'user'
}
```

- 通过 `window.__APP_ROUTE_MODE__` 全局变量存储当前路由模式
- 默认值为 `'user'`（用户端）
- 管理端通过设置该变量切换模式

#### 2. 标签页存储隔离

```typescript
// frontend/src/store/tab.ts
function resolveScopedTabStorageKey(key: string) {
  return `${key}:${getRuntimeRouteMode()}`
}

const scopedSessionStorage = {
  getItem(key: string) {
    return window.sessionStorage.getItem(resolveScopedTabStorageKey(key))
  },
  setItem(key: string, value: string) {
    window.sessionStorage.setItem(resolveScopedTabStorageKey(key), value)
  },
  removeItem(key: string) {
    window.sessionStorage.removeItem(resolveScopedTabStorageKey(key))
  },
}

export const useTabStore = defineStore('tab-store', {
  // ...
  persist: {
    storage: scopedSessionStorage,
  },
})
```

- Pinia 的 tab-store 持久化 key 根据路由模式分桶
- 实际写入 sessionStorage 时使用 `tab-store:user` / `tab-store:admin` 形式
- 避免跨端标签页污染

#### 3. 布局组件路由模式判断

```typescript
// frontend/src/layouts/index.vue
const isUserMode = getRuntimeRouteMode() === 'user'
```

- 布局组件根据路由模式显示不同的 UI
- 用户端和管理端可以有不同的布局结构

#### 4. 认证状态管理

```typescript
// frontend/src/store/auth.ts
async login(userName: string, password: string) {
  const mode = getRuntimeRouteMode()
  const authGuard = mode === 'admin' ? 'admin' : 'user'
  const { isSuccess, data } = await fetchLogin({ userName, password, authGuard })
  // ...
}

async initAuthRoute() {
  const routeMode = getRuntimeRouteMode()
  await routeStore.initAuthRoute(routeMode)
  // ...
}
```

- 登录时根据路由模式选择不同的认证守卫（`authGuard`）
- 初始化认证路由时根据路由模式加载对应的路由配置

## 管理员代登录安全加固

### 设计目的

管理员代登录时需要安全地传递会话信息，避免以下安全风险：
- 使用 `window.name` 传递 token 快照可能被恶意页面读取
- 跨域新窗口会话交接需要限制攻击面

### 实现方式

管理员代登录的新窗口会话交接改为：
- 同源新窗口 sessionStorage 一次性注入
- 限制 cross-origin target
- 不再使用 `window.name` 传递 token 快照

### 相关代码

- 管理员代登录逻辑在 `frontend/src/store/auth.ts` 中实现
- 使用同源新窗口打开，避免跨域风险

## Token 刷新机制

### 实现位置

- `frontend/src/service/http/token-refresh.ts`：Token 刷新逻辑

### 核心实现

```typescript
function getCurrentAuthGuard(): 'user' | 'admin' {
  return getRuntimeRouteMode() === 'admin' ? 'admin' : 'user'
}

export async function refreshAuthToken(refreshToken: string | null): Promise<LoginTokenPayload | null> {
  if (!refreshToken)
    return null
  const authGuard = getCurrentAuthGuard()
  // ...
}
```

- Token 刷新时根据当前路由模式选择对应的认证守卫。
- 同页由 `refreshPromise` 去重；跨页使用 Web Locks（不可用时回退 localStorage 租约）。
- 刷新锁和 BroadcastChannel 消息必须按 **refresh token 指纹** 隔离，不能仅用 `local/session + user/admin`；否则多个 login-as 窗口会互相覆盖 token。
- 刷新成功必须在释放锁前落盘 token，再广播给同一会话的其它标签，避免等待锁的标签拿旧 refresh token 二次轮换。
- 登出中的标签拒绝接收刷新广播，避免迟到结果把已退出会话写回。

## 用户端跨标签认证同步

- 普通用户端使用 localStorage，因此 `bootstrap.ts` 监听 `storage` 事件：其它标签登录后回填当前 Pinia 的用户信息、Presence 与自动刷新；其它标签退出后仅本地退出，不重复调用远端撤销。
- 路由守卫发现 localStorage 中已有 token、但 Pinia 尚未恢复时，会先调用 `authStore.hydrateFromStorage()`，避免“路由放行但页面没有用户信息”的状态分裂。
- 管理端和 login-as 使用 sessionStorage 隔离，**不参与**上述同步；强行同步会破坏多个独立管理会话。

```typescript
type AppRouteMode = 'user' | 'admin'
```

## 安全注意事项

1. **跨端隔离**：用户端和管理端的标签页状态完全隔离，避免污染
2. **会话安全**：管理员代登录使用 sessionStorage 一次性注入，避免 token 泄露
3. **路由模式**：通过全局变量 `window.__APP_ROUTE_MODE__` 控制路由模式，确保一致性
4. **Token 刷新**：按具体 refresh 会话协调刷新，避免跨端或 login-as 串 token
5. **跨标签同步边界**：仅用户端 localStorage 同步认证内存态；管理端 sessionStorage 保持独立

## 总结

前端路由与会话管理通过以下机制确保安全性和隔离性：
- 运行时路由模式管理
- 标签页存储隔离（基于路由模式的 sessionStorage 分桶）
- 管理员代登录安全加固（sessionStorage 一次性注入）
- Token 刷新机制（根据路由模式选择认证守卫）

这些机制共同确保了用户端和管理端的会话隔离和安全性。
